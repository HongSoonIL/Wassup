# 시험 주간의 서윤 · 첫 통합 기능 설계

4월 21일 수요일, 서윤이 군청색과 주황색으로 뽑은 포스터 사진을 올린다. 사용자가 그 사진에서 “그래서 결국 무슨 색 골랐어?”라고 묻는다. 그날 대화를 시작한 사람과 목요일에 처음 물어본 사람 모두 서윤이 주황을 골랐다는 사실을 들을 수 있어야 한다. 목요일에 통계 시험이 있다고 서윤에게 말한 사람에게만 시험 이야기가 이어진다.

이 문서는 Django 통합 기능의 **구현 계약**이다. 본문의 2027년 4월 일정과 식별자는 가상 학교의 테스트 데이터다. 11월의 클릭 시안은 [첫 베타 제품 설계](first-beta.md)에 있다.

| 구현 중 확인할 자료 | 용도 |
|---|---|
| [운영·사용자 API와 이벤트](exam-week-api.md) | 주간 승인 경쟁, 피드, 사진 인용 메시지, 프로필 왕복의 요청과 응답 |
| [생성·대화 프롬프트와 평가](exam-week-prompts.md) | 모델에 보내는 입력, 기대 출력, 두 캐릭터의 한국어 예문 |
| [시험 주간 검증 샘플](exam-week-sample.json) | 가상 시계, 승인·일정 수정, 발행 성공·실패, 두 계정의 기대 결과 |

프로젝트 루트에서 `python3 docs/design/check_exam_week.py`를 실행하면 샘플과 문서 속 JSON 예시의 ID·시각·사진·동의 범위를 대조할 수 있다. 각 시나리오는 지정한 체크포인트에서 독립적으로 시작한다. 샘플의 답장 예문은 한 번의 응답 내용을 나타낸다. 모델 출력은 캐릭터 설정에 따라 여러 말풍선으로 나눌 수 있다.

## 한 주를 준비하는 운영자

운영자는 학교 달력에 중간고사 기간과 체육대회 날짜를 입력한다. 생성기는 해당 주의 계절·요일, 학교 행사, 두 캐릭터의 반복 일과, 최근 공개한 사건과 사용 가능한 사진 목록을 읽는다. 봄이나 시험 기간은 소재를 고르는 단서다. 요일마다 사건을 만들거나 모든 글에 시험을 언급할 필요는 없다. 특정일 행사가 캐릭터 일정과 겹치면 충돌을 표시한다. 하루를 비워 둘 수 있다.

검토 화면에는 월요일부터 일요일까지 두 캐릭터를 나란히 두고, 각 후보의 근거 일정·사진·공개할 글·공개 시각을 보여준다. 운영자는 후보를 수정·제외하고 한 주를 한 번에 승인한다. 사진이 없거나 일정이 충돌한 후보는 이유를 보여주고 수정 또는 제외를 제공한다. 해결하지 않은 후보가 승인 대상에 있으면 전체 승인을 보류한다. 승인한 뒤의 달력 변경은 해당 일정을 참조하는 미발행 후보만 재검토 대상으로 돌린다.

## 저장할 기록과 소유권

| 기록 | 관계와 변경 규칙 |
|---|---|
| 학사 달력 항목 | 가상 학교의 기간 또는 하루 행사. 현지 날짜와 개정 번호를 기록한다. 한국 시각 기준 월요일에 한 주가 시작한다. 생성 시 읽은 달력 항목·개정 번호를 후보에 연결한다. |
| 주간 계획 | 같은 학교·시작일의 주차는 하나다. 두 캐릭터의 후보를 포함한다. 운영자가 본 계획의 revision으로 편집·승인을 요청하고, 오래된 요청에는 최신 계획을 다시 보여준다. |
| 게시 후보와 버전 | 하나의 게시물 ID에 캐릭터·사건·버전을 연결한다. 버전마다 근거 일정, 운영 메모, **대화에서도 사용할 공개 사실**, 피드 본문, 사진과 대체 텍스트, 공개 예정 시각을 보관한다. 본문·사진·근거 변경은 새 버전으로 기록한다. |
| 승인·발행 | 승인자는 주차와 게시물별 승인 버전·승인 시각을 남긴다. 공개 기록에는 실제 발행 시각과 정확한 게시 버전을 남긴다. 피드·프로필·인용 미리보기·대화 문맥이 이 기록을 같이 읽는다. 사진은 캐릭터에게 사용할 수 있는 자산이어야 한다. |
| 방·기억 | 기존 Friendship이 사용자와 캐릭터의 유일한 방이다. 기억에 방, 원본 메시지, 동의·삭제 상태를 연결하고 변경 시 방의 기억 개정 번호를 올린다. 공유 사건에 사용자 대화나 기억을 저장하지 않는다. |
| 메시지·답장 계획 | 기존 Message에 선택적 게시물 참조를 추가한다. 인용은 공개 당시의 버전을 식별할 수 있게 기록한다. 기존 메시지는 인용이 없는 텍스트로 읽는다. ReplyPlan에는 생성에 사용한 마지막 사용자 메시지, 공개 자료 버전, 기억 개정과 프롬프트 버전을 남긴다. |

프로필의 자기소개 한 줄은 기존 Character.status_message를 사용한다. “카페 알바 중” 같은 현재 활동은 해당 시각의 일과에서 읽는다. 나이·전공과 기존 Persona의 말투·예문은 캐릭터 설정에 둔다. 친구 목록·프로필·대화 헤더가 같은 인물과 현재 활동을 가리키도록 한다.

## 예약과 공개 경계

| 현재 상태 | 동작 | 결과 |
|---|---|---|
| draft | 편집·제외 | 수정하면 새 후보 버전, 제외하면 skipped. 사진 누락 등 검토 사유는 draft에 남긴다. |
| draft | 최신 주차를 묶음 승인 | 검증을 통과한 대상과 각 승인 버전을 한 트랜잭션에 기록하고 scheduled로 전환한다. 제외한 항목은 예약하지 않는다. |
| scheduled 또는 failed | 관련 행사·콘텐츠 변경 | 해당 후보의 승인을 무효화한다. 다음 버전은 draft가 되고 이전 버전의 예약이나 재시도로는 발행할 수 없다. 다른 예약은 원래 시각을 유지한다. |
| scheduled | 서버 시계가 예정 시각에 도달 | 승인 버전과 현재 버전을 일치시킨 뒤 해당 버전을 published로 한 번 공개한다. 자산 준비에 실패하면 failed와 원인을 남긴다. |
| failed | 같은 승인 버전 재시도 | 원래 게시물 ID로 재시도한다. 성공한 시점부터 공개한다. 이미 성공한 작업의 재전달은 공개 기록을 늘리지 않는다. |

발행 워커는 외부 파일 확인을 DB 잠금 밖에서 수행한다. 마지막 트랜잭션에서 주차와 후보를 편집 경로와 같은 순서로 잠그고 최신 승인·예정 시각·사진 준비 상태를 다시 확인한다. 공개 기록에는 게시물·버전의 유일성 제약을 둔다. 작업이 중간에 멈춰도 DB의 예약을 다시 조회할 수 있다. 화면 갱신 신호는 커밋 뒤 전송하며, 다시 접속한 사용자는 DB 조회로 결과를 복원한다.

사용자 조회는 요청자의 친구 관계, 실제 발행 성공, 공개 시각을 함께 확인한다. 사진 원본·썸네일·대체 텍스트에도 같은 공개 조건을 적용한다. 시안 번들의 정적 이미지 경로는 서버 기능에서 재사용할 공개 URL이 아니다. 미리보기는 운영자 권한으로만 읽는다. 달력에서 체육대회가 연기돼도 이미 공개된 수요일 포스터와 그 사실은 유지한다.

## 인용한 사진에서 다음 날 대화까지

피드에서 ‘서윤에게 말 걸기’를 누르면 기존 방에 사진 인용 미리보기와 빈 입력창이 열린다. 사용자가 직접 보내야 메시지가 생성된다. 채팅 헤더의 이름·사진 또는 상대 말풍선 옆 얼굴을 눌러 프로필을 볼 수 있다. 닫기와 뒤로 가기는 기존 방, 읽던 메시지, 입력 중인 글과 인용 사진을 복원한다. 방 상태는 계정과 방 ID로 구분한다.

서버가 메시지를 수락할 때 방 소유권과 인용 대상을 함께 검사한다. 전송이 실패하면 입력과 인용을 유지해 사용자가 수정할 수 있게 한다. 새 메시지가 대기 중에 도착하면 기존 ReplyPlan의 최초 기한을 유지하면서 생성 입력을 갱신한다. 모델 호출은 방 잠금 밖에서 실행한다. 발송 시점에는 원본 게시물·방 기억·최근 메시지 버전을 다시 확인한다. 삭제된 기억이 포함된 생성 결과는 버린다. 남은 시간에 새 결과를 얻지 못하면 해당 캐릭터의 검수된 짧은 문장으로 기한 안에 답한다.

## 첫 통합의 인수 기준

| 시나리오 | 확인할 결과 |
|---|---|
| 사진 누락과 동시 승인 | 누락 후보를 보여주고 운영자가 제외하면 나머지를 한 번에 승인한다. 두 번째 운영자의 오래된 편집이나 승인은 기존 예약을 덮지 않는다. |
| 경기 연기 | 체육대회를 연기하면 그 행사에 의존하는 후보만 재검토한다. 오래된 워커가 행사 사진을 발행할 수 없고 포스터 예약은 유효하다. |
| 시각 경계·장애 | 발행 직전에는 두 계정의 피드·프로필·사진·인용 요청·모델 입력 모두 포스터를 공개하지 않는다. 실패하면 이전 공개본만 조회된다. 재시도 성공 뒤 두 계정에 같은 한 건이 보인다. |
| 인용·프로필 왕복 | 피드에서 인용 후 문장을 쓰다가 상대 프로필을 열고 뒤로 간다. 같은 방의 스크롤·초안·인용이 유지된다. 인용 없는 기존 요청도 그대로 전송된다. |
| 다음 날·기억 삭제 | 두 방의 공개 답은 ‘주황’이다. A–서윤의 시험 기억은 B–서윤과 A–도현에서 조회되지 않는다. A가 생성과 발송 사이에 삭제하면 이후 답장에 시험 이야기가 없다. |
| 재접속·최초 기한 | 깨어 있을 때 보낸 첫 메시지 뒤에 질문을 더 보내고 앱을 닫는다. 3시간 이내에 최신 질문을 반영한 첫 답장이 저장된다. 워커 재실행과 이벤트 재전달을 거쳐도 한 번 보인다. |

## 구현 인계 순서

1. **발행·조회** — Django·PostgreSQL에 달력, 주간 후보·버전과 공개 기록을 추가한다. 가상 시계와 두 계정으로 일괄 승인, 변경 충돌, 독립적인 예약, 미발행 사진 접근 차단을 검사한다.
2. **사진 인용과 프로필** — 기존 메시지 조회·전송·방 이벤트에 선택적 인용을 연결한다. nullable 참조를 먼저 배포해 기존 방과 메시지를 읽을 수 있게 한다. 두 계정으로 사진에서 방에 진입하고 프로필에서 돌아오는 경로를 확인한다.
3. **LLM 연결** — 주간 생성과 답장 생성을 별도 호출로 붙인다. 검증 입력으로 고정 응답 테스트를 먼저 통과시킨 뒤 개발 키로 실제 한국어 답변을 평가한다. 모델 버전별 지연·호출 비용·대체 답장 횟수를 집계한다.
4. **두 계정 통합 검증** — PostgreSQL·워커·Redis와 두 브라우저 세션으로 위 인수 기준을 재현한다. 발행 시도·결과, 예약 대비 지연, 답장 기한 초과를 ID·버전 기준으로 기록한다. 운영 현황에는 개인 대화 본문이나 기억 원문을 싣지 않는다.

현재 일반 API는 세션 인증과 CSRF를 쓰며 방 ID는 Friendship의 기본키다. 예약 답장·실시간 이벤트까지 연결한 검증본의 기준 커밋은 `9d11a21`이다. 구현을 시작할 때 이 기반에서 채팅 전송과 재접속부터 확인하고 새 계약을 붙인다. [기존 메시지 API](../chat-api.md)
