# 모바일 채팅방 API와 동작 확인

## 현재 Django API

`/signup/`에서 가입하거나 `/login/`에서 로그인한 뒤 `/discover/`에서 친구를 추가한다. 같은 브라우저에서 `GET /api/friends/`를 열어 `friends[].room_id`를 확인한다. 이 값이 채팅방 번호다. 채팅방 헤더에는 같은 항목의 `character.name`, `status_message`, `profile_image`를 사용한다. 친구 홈에는 `friends[].current_activity`로 해당 시각에 진행 중인 일과를 표시한다. 현재 일과·프로필 이미지·마지막 메시지는 각각 `null`일 수 있다.

| 요청 | 성공 응답과 화면 동작 |
|---|---|
| `GET /api/characters/` | 공개 프로필 목록 `characters`를 반환한다. 각 항목의 `room_id`는 이미 추가한 친구의 방 번호이며, 추가 전에는 `null`이다. |
| `POST /api/friends/` | `{"character_id":1}`를 보내면 `{"room_id":3}` 형식으로 방 번호를 반환한다. 새 방은 `201`, 이미 친구면 `200`이다. |
| `GET /api/rooms/{room_id}/messages/` | `200`. `{"messages": [], "has_more": false}` 형식. 기본 30개를 오래된 순서로 표시한다. 이전 페이지는 가장 작은 메시지 ID를 `before`에 넣어 요청한다. |
| `POST /api/rooms/{room_id}/messages/` | `{"text":"뭐해?"}`를 보내면 `201`과 `{"id":41,"status":"sent","created_at":"2026-11-26T18:40:00+09:00"}`가 돌아온다. 보낸 본문과 반환된 ID로 내 말풍선을 표시한다. |
| `POST /api/rooms/{room_id}/read/` | 사용자가 열린 방에서 본 상대 말풍선의 ID를 `{"through_id":42}`로 보낸다. 서버가 그 ID까지 받은 말풍선을 읽음 처리하고 남은 `unread_count`를 돌려준다. |

최신 기록 조회는 현재 일과 `current_activity`와 실제로 입력 중인 경우 종료 시각 `typing_until`도 반환한다. 다시 연결한 탭은 이 값으로 입력 표시를 복원한다. 모든 요청은 로그인 세션을 사용한다. 먼저 GET으로 받은 `csrftoken` 쿠키 값을 POST의 `X-CSRFToken` 헤더에 넣고 `Content-Type: application/json`을 지정한다. 공백뿐인 메시지 또는 1,000자를 초과한 본문은 `400`이다. `401`이면 로그인이 필요하다. `403`이면 방 접근 권한 또는 CSRF 토큰을 확인하고, `404`이면 방 번호를 확인한다. 네트워크가 응답 전에 끊기면 메시지가 이미 저장됐을 수 있으므로 기록을 조회한 뒤 재전송 여부를 결정한다.

## 예약 답장 이벤트

아래 시간표는 UI와 서버 작업자가 함께 재현할 수 있는 예시다. 메시지와 발송 결과는 PostgreSQL에 저장하며, 열린 채팅방은 같은 주소의 `/ws/chat/{room_id}/`에서 실시간 이벤트를 받는다.

| 현지 시각 | 예시 데이터 | 화면 |
|---|---|---|
| 18:40 | POST 성공. 내 메시지 ID는 `41`, 상태는 `sent`. | “뭐해?” 옆에 읽지 않음 숫자 1 |
| 20:10:00 | `{"type":"message.read","message_id":41,"read_at":"2026-11-26T20:10:00+09:00"}` | 41번 말풍선의 1이 사라짐 |
| 20:10:01 | `{"type":"typing.start"}` | 도현이 입력 중 |
| 20:10:04 | `{"type":"typing.stop"}`, 이어서 `message.new` | 입력 중 표시가 사라지고 도현의 첫 답장이 도착 |

후속 말풍선이 있으면 앞 말풍선을 실제 보낸 뒤 1~2초 쉬고 다시 입력을 시작한다. 입력 시간은 문장 길이와 캐릭터의 타자 속도에 따라 2~8초다. 이 사이 사용자가 말을 걸면 아직 도착하지 않은 문장들을 취소한다. 마지막 말풍선을 보낸 지 30초 이내라면 휴대폰을 이미 보고 있는 상황으로 간주해 새 메시지를 빨리 확인할 수 있다. 수면과 집중 일정도 함께 적용한다.

`message.new`는 아래처럼 GET의 메시지 한 건과 같은 필드를 전달한다. 이벤트 구독은 해당 채팅방으로 한정한다.

```json
{
  "type": "message.new",
  "message": {
    "id": 42,
    "sender": "character",
    "kind": "text",
    "text": "지금 잠깐 쉬는 중 ㅋㅋ",
    "status": "sent",
    "created_at": "2026-11-26T20:10:04+09:00",
    "read_at": null
  }
}
```

## PR 검증 기준

- **채팅 화면.** 로그인한 사용자가 자신의 방에서 기록을 조회하고 메시지를 보낸다. 새로고침하면 저장된 메시지가 한 번 표시된다. 전송에 실패하면 입력한 문장이 남는다. 고정 이벤트는 테스트 모드에서 읽음·입력 중·답장 순서로 재생한다.
- **예약 답장 서버.** 서버 시계로 읽을 시각과 답장 시각을 정하고 상태를 DB에 기록한다. 첫 시연에서 18시 40분에 도현이 받은 메시지에는 21시 40분까지 첫 답장이 도착한다. 추가 메시지가 와도 최초 발송 기한을 지키고 최신 대화가 반영된다. 워커 재시작 후 같은 답장이 중복 저장되지 않는다.
- **통합.** 휴대폰에서 전송 후 탭을 닫고 답장 시각 뒤 다시 열면 실제 기록에서 도현의 답장을 한 번 읽을 수 있다. 이미 열린 방은 같은 메시지 ID의 재수신을 합친다. 두 계정은 각자 자기 방의 기록과 이벤트만 받는다.

## 실행

React 단독 미리보기는 서버와 독립적으로 실행한다. 프로젝트 루트에서 다음 명령을 실행한 뒤 Vite가 표시한 로컬 주소를 연다.

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

미리보기는 샘플 대화를 메모리에 표시한다. 전송하면 읽음·입력 중·고정 답장 순서를 재생하고, 새로고침하면 예시로 돌아간다. 캐릭터와 카페 이미지는 팀 기획서에 수록된 가상 인물·장면을 사용했다.

Django에서 실제 기록을 사용하려면 같은 frontend 디렉터리에서 `pnpm build`를 실행한다. 프로젝트 루트로 돌아와 README의 DB 초기 설정과 시드를 완료하고 `python manage.py runserver`로 실행한다. `/`에서 가입하고 친구를 추가한 뒤 프로필의 **대화하기**를 눌러 방에 들어간다. 서버에 연결된 화면은 워커가 저장한 메시지를 WebSocket과 REST로 받아 표시한다. 탭에 복귀하거나 연결을 복구할 때 REST로 최신 기록을 확인한다.

## 예약 발송 통합 실행

로컬 채팅 화면과 함께 예약 답장을 확인하려면 Redis를 포함해 Docker Compose 서비스를 실행한다. Django는 `python manage.py runserver`로, 별도 터미널의 발송 워커는 `python manage.py run_reply_worker`로 실행한다. 둘 다 같은 환경 변수와 PostgreSQL·Redis에 연결한다.

개발 환경에서 빠르게 시연하려면 Django 웹 프로세스에 `DJANGO_DEBUG=True WASSUP_REPLY_DEMO_SECONDS=2`를 적용한다. 이 설정에서는 새 메시지의 일정이 초 단위로 압축된다. 일반 설정에서는 캐릭터의 한국 시각 일과, 답장 속도와 타자 속도로 읽음·입력·발송 시각을 따로 예약한다. 한가할 때 최근 5분 안에 주고받은 방은 다음 확인이 빨라진다. 깨어 있을 때의 첫 답장 기한은 3시간이고 수면은 기상 시각을 반영한다. 워커는 발송 예정 2분 전부터 답장을 미리 생성할 수 있다. 답장 계획의 `generation_ms`는 모델 호출 소요 시간이다.

1. 로그인한 계정으로 `/chat/{room_id}/`를 열고 메시지를 두 건 보낸다.
2. 실시간 연결에서 읽음, 입력 중, 새 답장 순서를 확인한다.
3. 다음 메시지를 보낸 뒤 탭을 닫고 발송 시각이 지난 뒤 다시 연다. 도착한 말풍선마다 고유한 메시지 ID가 하나씩 있고 새로고침 후에도 순서와 개수가 유지된다.

예약은 PostgreSQL에 저장한다. 각 말풍선 저장과 그다음 발송 위치 갱신은 한 트랜잭션이며, Redis는 열린 채팅방에 화면 이벤트를 전달한다. 기본 설정에서는 발행된 글과 질문에 맞춰 샘플 답장을 선택한다. 서버에서 OpenAI를 설정하면 같은 대화 문맥으로 답장을 생성한다. [서버 설정](../README.md#피드-사진으로-대화하기)


## 친구별 대화 기억 API

인증과 CSRF는 메시지 API와 같다. 기억을 관리할 방의 친구 관계를 서버에서 확인한다.

| 요청 | 동작 |
|---|---|
| `GET /api/rooms/{room_id}/memories/` | `enabled`, `revision`, `memories`를 반환한다. 각 항목에는 종류, 내용, 일정 날짜, 원본 메시지 ID와 본문이 있다. |
| `PATCH /api/rooms/{room_id}/memories/` | `enabled`와 `expected_revision`을 보낸다. 끄면 해당 방의 기억을 모두 삭제한다. |
| `PATCH /api/rooms/{room_id}/memories/{id}/` | 변경할 `text` 또는 `event_date`와 `expected_revision`을 보낸다. |
| `DELETE /api/rooms/{room_id}/memories/{id}/` | JSON 본문에 `expected_revision`을 보내 한 항목을 삭제한다. |

변경이 성공하면 갱신된 목록을 반환한다. 편집 중 다른 작업으로 목록이 바뀌면 서버가 409를 반환한다. 최신 목록을 읽고 다시 편집할 수 있다. 기억 수정·삭제·끄기 이전까지의 방 메시지는 화면에서 계속 볼 수 있다. 모델의 최근 대화 입력은 변경 이후의 메시지부터 다시 쌓아, 예전 대화에서 삭제하거나 고친 사실을 되찾는 일을 막는다.
